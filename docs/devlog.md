### 2. 实现内容

#### 2.1 整体链路
```
抖音直播间 URL
   │  DouyinSource.resolve()   —— httpx 请求抖音 Web 接口
   ▼
StreamInfo（主播名 / 标题 / 在线人数 / flv 拉流地址 / 请求头）
   │  ffmpeg 子进程            —— 拉 flv、丢弃视频、重采样
   ▼
16kHz / 单声道 / s16le PCM，每 100ms 一块（3200 字节）
   │  AudioStream 迭代器       —— 断流自动重连
   ▼
scripts/record.py 写 WAV + 元数据 JSON   （D2 起改为喂给 ASR）
```

#### 2.2 模块明细

| 文件 | 技术 | 功能 |
|---|---|---|
| `livewatch/sources/base.py` | Python ABC + dataclass | 数据源抽象：`StreamSource`（`match()` 判断能否处理输入、`resolve()` 解析拉流地址）、`StreamInfo`（统一的流信息结构）、`StreamOffline` 异常 |
| `livewatch/sources/douyin.py` | httpx | 抖音直播间解析，详见 2.3 |
| `livewatch/sources/file.py` | ffmpeg `-re` | 本地音视频文件当作"直播"，按真实速度读取 |
| `livewatch/sources/__init__.py` | 简单注册表 | `get_source(target)` 依次调用各数据源的 `match()`，自动选择数据源 |
| `livewatch/audio.py` | subprocess + ffmpeg | 音频管线 + 断流重连，详见 2.4 |
| `scripts/record.py` | argparse + wave | 录样本命令行工具，Ctrl+C 可提前安全结束（SIGINT → `stream.stop()`，WAV 头正常写入） |
| `pyproject.toml` | uv | 依赖管理（目前只有 httpx） |

#### 2.3 抖音解析的具体做法
1. 从 URL 中用正则 `live\.douyin\.com/(\d+)` 提取直播间号 `web_rid`（也支持直接输入数字）。
2. 先 GET `https://live.douyin.com/` 拿游客 cookie `ttwid`（httpx.Client 自动保存）。
3. GET `https://live.douyin.com/webcast/room/web/enter/?web_rid=...&aid=6383&...`，返回 JSON 中：
   - `data.data[0].status`：`2` 表示直播中
   - `data.data[0].title` / `user_count_str`：标题、在线人数
   - `data.user.nickname`：主播名
   - `data.data[0].stream_url.flv_pull_url`：`{FULL_HD1, HD1, SD1, SD2}` 四档 flv 地址（另有 `hls_pull_url_map` 同样四档）
4. 按 `SD2 → SD1 → HD1 → FULL_HD1` 的顺序选第一个可用地址。
5. 返回的请求头带上 UA 和 Referer，ffmpeg 拉流时通过 `-headers` 传入。

#### 2.4 音频管线的具体做法
ffmpeg 命令（核心参数）：
```
ffmpeg -nostdin -headers "User-Agent:...\r\nReferer:...\r\n" -rw_timeout 10000000 \
       -i <flv地址> -vn -ac 1 -ar 16000 -f s16le pipe:1
```
- `-vn` 丢弃视频；`-ac 1 -ar 16000` 转成单声道 16kHz；`-f s16le pipe:1` 把裸 PCM 写到 stdout。
- `-rw_timeout 10000000`（单位微秒）：10 秒读不到数据就让 ffmpeg 退出，避免网络卡死时进程一直挂着。
- 本地文件加 `-re`，按真实播放速度输出，模拟直播节奏。

`AudioStream.__iter__` 的重连逻辑：
1. 每轮先 `resolve()` 拿**新的**拉流地址；如果抛出 `StreamOffline`，说明主播下播，正常结束。
2. 启动 ffmpeg，循环 `stdout.read(3200)` 产出 100ms 音频块。
3. ffmpeg 退出后：如果是用户主动停止或本地文件，直接结束；否则视为断流。
4. 退避等待 `min(2^n, 30)` 秒后重连。只要上一轮拉到过数据，失败计数 n 就清零；连续 5 次一点数据都没拉到才报错退出。

### 3. 技术取舍

| 决策点 | 选择 | 放弃的方案 | 理由 |
|---|---|---|---|
| 获取直播音频的方式 | 解析平台接口拿 flv 地址，再用 ffmpeg 拉流 | ① 系统音频采集（BlackHole / WASAPI loopback）② 浏览器自动化录制 | 拉流方式不需要开播放器、不受系统音量和其他声音干扰、能无头并发多个直播间；缺点是每个平台都要单独适配、可能被风控。系统音频采集作为"任何平台都能用"的兜底方案，留到后面实现 |
| 拉流清晰度 | 最低档 SD2 | FULL_HD1 | **实测**各档音频完全相同（AAC 48kHz 双声道 ~104kbps），只有视频不同：SD2 720×1280 约 2Mbps，FULL_HD1 1080×1920 约 6Mbps。flv 是音视频混合流，视频数据无论如何都要下载，选最低档带宽省约 2/3，同时盯多个直播间时更关键 |
| flv 还是 HLS(m3u8) | flv | m3u8 | flv 是长连接持续推送，延迟约 1～3 秒；HLS 按切片下载，通常有 5～10 秒以上延迟。盯播要实时，选 flv |
| 输出音频格式 | 16kHz / 单声道 / 16bit PCM | 保留原始 48kHz 双声道 AAC | 讯飞、SenseVoice、Paraformer 等主流中文 ASR 都要求这个格式；在入口处统一，下游所有模块都不用再关心格式 |
| 音频怎么交给下游 | ffmpeg 写 stdout，Python 迭代器按 100ms 分块 | 先落盘再读文件；用 PyAV 等库在进程内解码 | 子进程方式最简单，ffmpeg 崩溃不会拖垮主进程；迭代器接口让"录到文件"和"送去 ASR"可以用同一份代码。100ms 是流式 ASR 常见的送帧粒度 |
| 断流怎么处理 | 每次重连都重新 resolve 拿新地址 + 指数退避 | 只重试旧地址；用 ffmpeg 自带 `-reconnect` 参数 | 拉流地址带 `expire`/`sign` 签名会过期，旧地址重试可能永远失败；只有重新解析才能拿到新签名，同时也能顺便发现主播已下播 |
| 数据源设计 | 抽象接口 + 注册表 | 把抖音逻辑直接写进主流程 | 题目要求"能盯所有直播间"，接口抽象让新增平台只需加一个类；`FileSource` 让开发和演示不依赖直播是否在线（演示当天直播间很可能没开播） |
| 项目工具 | uv | pip + venv / poetry | 速度快、自带锁文件（`uv.lock`），换电脑或打包时能复现同样的依赖 |

### 4. 遇到的问题与解决

#### 问题 1：直接请求房间接口返回空响应
- **现象**：带好 UA 和 Referer 直接请求 `webcast/room/web/enter`，HTTP 状态码 200，但**响应体长度为 0**，`json()` 抛出 `JSONDecodeError`。
- **排查**：状态码正常说明不是被直接拦截；对比浏览器访问，发现浏览器会先拿到 `ttwid` 这个 cookie。
- **原因**：抖音 Web 接口会校验游客 cookie `ttwid`，没有就静默返回空响应（不报错，比较隐蔽）。
- **解决**：`_ensure_cookie()` 先访问 `https://live.douyin.com/` 让服务端下发 `ttwid`，复用同一个 `httpx.Client` 自动携带。
- **复盘**：返回 200 加空内容是典型的"软拦截"。代码里在 `data.data` 为空时抛出明确的 `RuntimeError("接口未返回房间数据（可能被风控）")`，避免后面出现莫名其妙的 KeyError。

#### 问题 2：缺少部分 query 参数时同样返回空响应
- **现象**：写验证脚本时去掉了 `screen_width / screen_height / browser_language / browser_platform` 四个参数，即使带了 cookie，响应体长度也是 0；补回去后正常（约 44KB）。
- **原因**：接口会校验这些"浏览器指纹"类参数是否完整。
- **解决**：生产代码中保留完整参数列表，并在 `douyin.py` 中集中维护。
- **复盘**：抖音接口参数随时可能变化，这是适配层最脆弱的地方。好在已经被封装在 `DouyinSource` 内，接口变了只需改这一个文件。后续可以考虑加一个定时自检。

#### 问题 3：`uv sync` 构建失败
- **现象**：`uv sync` 报 setuptools "package discovery" 错误。
- **原因**：`pyproject.toml` 里设了 `tool.uv.package = true`，uv 会把项目当作包来构建；setuptools 的 flat-layout 自动发现机制看到根目录下有 `livewatch/`、`scripts/`、`samples/` 多个目录，无法判断哪个是要打包的包，于是拒绝构建。
- **解决**：现阶段只是用 `uv run` 运行脚本，不需要把项目安装成包，改为 `package = false`；`scripts/record.py` 通过 `sys.path` 引入 `livewatch`。
- **后续**：做桌面端打包时需要重新考虑包结构（例如改为 `src/` 布局，或显式声明 `packages`）。

#### 问题 4：样本音量偏高，可能削波（待验证）
- **现象**：20 秒测试样本 `volumedetect` 结果为平均音量 -10dB、峰值 0dB。峰值顶到 0dB 说明可能有削波（波形被截平）。
- **分析**：带货直播通常主播用麦克风贴近讲话，同时叠加背景音乐，整体响度较高。
- **影响**：削波和背景音乐都可能降低 ASR 准确率。
- **计划**：D2 在 ASR 对比时专门观察：有背景音乐的段落字错率是否明显变高。如果影响大，考虑 VAD（语音活动检测）过滤纯音乐段，或做音量归一化。

### 2. 实现内容

#### 2.1 语音识别（`livewatch/asr.py`）
- **技术**：sherpa-onnx 运行 SenseVoice int8 量化模型（约 230MB 解压后）+ Silero VAD。
- **伪流式做法**：SenseVoice 本身不支持流式，用 VAD 检测停顿切句，每切出一句就送去识别；设置了 `max_speech_duration=12s` 希望强制切长句，但实测句长 7–25 秒（中位约 16 秒），说明该参数在 sherpa-onnx 中是"软限制"（超时后提高阈值等待停顿，而非硬切）。带货主播语速快、停顿少，单句识别延迟最长约 25 秒，对 1 分钟分析周期可接受，见遗留问题。
- **附加信息**：SenseVoice 一次推理同时输出情绪标签（HAPPY / ANGRY / NEUTRAL…）和声音事件（BGM / Laughter…），直接展示在转写里，零额外成本。
- **`use_itn=True`**：逆文本标准化，输出"399""7天"而不是"三百九十九""七天"，并带标点，方便后续匹配价格等信息。
- **离线转写工具** `scripts/transcribe.py`：输出 JSONL 并统计 RTF。

#### 2.2 话术框架（`config/frameworks/*.yaml` + `livewatch/framework.py`）
题目没给框架格式，自己定义了一套结构化 YAML：
- `product`：品牌、单品、卖点、合规注意事项
- `thresholds`：语速快慢、冷场秒数、讲话占比、口头禅密度阈值
- `stages`：8 个话术阶段（开场留人 / 产品介绍 / 核心卖点 / 信任背书 / 价格与福利 / 促单逼单 / 售后保障 / 互动），每个阶段写清"必须讲到什么"
- `rules`：节奏要求（如"每 5 分钟至少完整报一次价"）
- `asr_corrections`：ASR 纠错表（韩数→韩束、浅店→旗舰店）
- `extra_banned`：自定义违禁词

界面里可以直接编辑 YAML，保存时先 `yaml.safe_load` 校验格式；框架名做了路径校验，防止 `../` 越权写文件。

#### 2.3 表达指标（`livewatch/metrics.py`）—— 本地确定性计算
| 指标 | 算法 |
|---|---|
| 语速 | 有效字数（只计汉字 / 字母 / 数字）÷ 讲话时长 × 60，单位字/分 |
| 讲话占比 | 语音段时长之和 ÷ 窗口时长 |
| 最长冷场 | 相邻语音段之间（含窗口首尾）的最大空白 |
| 口头禅 | "那个 / 然后 / 就是 / 对吧…" 每百字出现次数 |
| 重复度 | 8 字片段的重复占比，用于发现车轱辘话 |
| 情绪分布 | SenseVoice 情绪标签计数 |

指标超过框架阈值就生成告警（带 `code` 用于去重）。

#### 2.4 违禁词（`livewatch/rules.py`）
- 内置四类词库：广告法极限用语、化妆品功效夸大、医疗用语、站外引流，每类带法规依据说明。
- 编译成一个正则，**长词优先**匹配；每识别一句扫描一次，秒级告警，不等大模型。
- **防误报**：不收录单字"最""第一"（会命中"最后""第一场"），只收组合词（"全网最低""销量第一"）。

#### 2.5 大模型分析（`livewatch/analyzer.py`）
- **接口**：OpenAI 兼容的 `/chat/completions`，用 httpx 直接调用（不引入 SDK），`.env` 配置 `LLM_BASE_URL / LLM_API_KEY / LLM_MODEL`，默认 DeepSeek，换通义千问、Kimi 只改配置。
- **输入**：话术框架（格式化为文本）+ 本地指标 + 最近 N 分钟转写（每句带 `[mm:ss]` 相对时间）。
- **输出**：`response_format=json_object` 强制 JSON，包含 `summary / current_stage / stage_coverage / issues / score`。
- **Prompt 设计要点**：
  - 问题必须从**固定编码列表**中选（`missing:<阶段>`、`compliance:efficacy`、`content:pressure`…），保证可以按编码去重和统计；
  - 明确告诉模型"语速、冷场、口头禅已由本地规则检测，不要重复报告"，避免职责重叠；
  - 要求 `quote` 必须是原文片段，问题附证据，减少幻觉；
  - 提醒"转写可能有错别字，不要因此判定问题"；
  - 最多 5 条，按严重程度排序，避免告警泛滥。
- 记录每次调用的延迟和 token 数（`_meta`），用于估算成本。

#### 2.6 会话引擎（`livewatch/session.py`）
- 每个直播间一个 `RoomSession`：音频线程（拉流 → ASR → 违禁词）+ 单线程分析池（指标 + LLM），事件通过 `emit` 回调推出。
- **时间基准用"音频时间"而不是墙上时钟**：直播、1 倍回放、10 倍回放用同一套调度逻辑；断流重连期间时间不前进，不会误报冷场。
- **调度**：音频时间每跨过一个 `interval` 触发一次分析；上一次 LLM 调用还没返回时跳过本次，防止请求堆积。
- **告警去重**：以问题编码为键，在一个分析窗口（默认 5 分钟）内再次出现只累加次数（界面显示 ×N），超过窗口才重新提醒。
- **落盘**：`sessions/<时间>_<id>/` 下保存 `segments / metrics / analyses / alerts` 的 JSONL 和 `meta.json`，方便复盘和离线调 Prompt。
- **场次报告**：全场平均语速、讲话占比、告警按来源统计、评分趋势、重点问题 Top 10。

#### 2.7 服务与界面（`livewatch/server.py`、`web/index.html`、`app.py`）
- FastAPI：REST 管理直播间（增 / 停 / 删 / 报告）、读写话术框架；WebSocket 推送实时事件。
- 后台线程 → asyncio：`loop.call_soon_threadsafe(queue.put_nowait, msg)` 投递到每个 WebSocket 客户端的队列。
- 服务只监听 `127.0.0.1`，端口自动选空闲端口。
- 界面：单 HTML 文件，原生 JS，无构建步骤。布局：顶部添加栏 → 直播间标签页 → 指标卡片 → 三栏（实时转写 / 告警 / AI 分析 + 语速趋势图）。违禁词在转写中标红，高危告警右下角弹窗，告警可按来源筛选。
- `app.py`：后台线程起 uvicorn，pywebview 打开原生窗口；`--browser` 参数用浏览器打开便于调试。

### 3. 技术取舍

| 决策点 | 选择 | 放弃的方案 | 理由 |
|---|---|---|---|
| ASR | 本地 SenseVoice（sherpa-onnx） | 讯飞 / 阿里云实时转写 | 免费、免密钥、数据不出本机、演示不依赖网络；**实测比实时快约 30 倍**，单机可并发多个直播间。代价是不支持热词（品牌名会错），用纠错表弥补；伪流式有句长级延迟，但分析周期是 1 分钟，可接受 |
| 流式方式 | VAD 切句 + 离线模型 | 真流式模型（Paraformer-streaming） | SenseVoice 中文准确率更好，还带情绪和 BGM 识别；盯播不需要逐字上屏的低延迟 |
| 指标计算 | 本地规则 | 交给 LLM 判断 | 零成本、零延迟、结果稳定可解释；LLM 不擅长数数 |
| 违禁词 | 本地词库实时匹配 + LLM 语义补充 | 只靠 LLM | 违禁词是最高风险项，需要秒级告警；词库抓不到的变体（如"王总来炸福利"这类虚构紧迫）交给 LLM |
| 分析粒度 | 表达指标看最近一个周期；LLM 看最近 5 分钟 | 都看 5 分钟 | 表达问题要及时，且 5 分钟窗口每分钟滑动会把同一次冷场报 5 次；话术结构需要更长上下文才能判断阶段是否缺失 |
| LLM 接入 | OpenAI 兼容接口 + httpx | 绑定某家 SDK | 一套代码切换多家模型，方便对比成本和效果 |
| 输出格式 | JSON mode + 固定问题编码 | 自由文本 | 可以程序化去重、统计、展示 |
| 桌面框架 | pywebview + 本地 Web 服务 | Electron / Tauri / PySide | 单一 Python 技术栈，ASR 生态最好；界面用 Web 写得快；同一界面也能在浏览器调试 |
| 前端 | 单 HTML 原生 JS | React + 构建工具 | 一天工期，零构建、零依赖，打包时只是一个静态文件 |
| 时间基准 | 音频时间 | 墙上时钟 | 回放倍速、断流重连都不会打乱调度 |

### 4. 遇到的问题与解决

#### 问题 1：冷场误报（"最长 16.8 秒无人讲话"，实际主播一直在讲）
- **现象**：引擎测试中第 1 分钟就报"出现冷场"，但听录音主播没停过。
- **排查**：打印语音段时间，发现 43.3s–61.0s 这句在 t=60s 分析时还没被识别出来。
- **原因**：VAD 要等一句话结束（或达到最大句长）才切出语音段。分析时刻主播正在讲的那句不在结果里，末尾空白就被当成了冷场。
- **解决**：分析时查询 VAD 的 `is_speech_detected()`，如果此刻仍在讲话（`open_tail`），窗口末尾空白算"讲话中"，不计入冷场。
- **复盘**：流式系统里"还没识别出来"和"没人说话"是两回事，指标计算要区分。

#### 问题 2：语速虚高（559 字/分）
- **现象**：第 2 分钟语速 559 字/分，明显不合理（正常带货 250–400）。
- **原因**：跨窗口边界的句子，讲话时长只算了窗口内的部分，字数却全算进来了。句子越长（这里有 25 秒的长句），误差越大。
- **解决**：跨边界的句子按时长比例分摊字数。修复后三个周期分别是 382 / 386 / 333 字/分，与整体估算（3 分钟约 400 字/分）一致。

#### 问题 3：10 倍速回放实际只有约 1.8 倍
- **现象**：界面上设置 10 倍速回放，时钟每秒只走约 1.8 秒；CPU 几乎空闲，说明不是算力瓶颈。
- **排查**：单独测 ffmpeg：`-readrate 6` 处理 30 秒音频用时 5.3 秒（正常），`-readrate 10` 反而用了 16.9 秒。
- **原因**：ffmpeg 8 的 `-readrate` 对 WAV 输入在高倍率下行为异常（具体机制未深究）。
- **解决**：不再依赖 ffmpeg 控速。ffmpeg 全速解码，在 Python 侧按"已送出音频时长 ÷ 倍速"计算应到时间，提前了就 sleep。实测 10.1 倍，且任意倍速都准确。
- **复盘**：节奏控制放在自己代码里，可控、可测，也不依赖 ffmpeg 版本。

#### 问题 4：新建直播间后状态一直显示"连接中"
- **原因**：竞态。后端线程启动很快，WebSocket 推来的"盯播中"状态比 POST 接口的响应先到；随后 POST 返回的旧快照（starting）把新状态覆盖了。
- **解决**：POST 返回时，如果该直播间已经由 WebSocket 事件创建，就不再用旧快照覆盖。

#### 问题 5：ASR 专有名词错误
- **现象**：韩束→"韩数"，旗舰店→"浅店"，7 天无理由→"7 天无流"。
- **原因**：SenseVoice 不支持热词，品牌名、电商术语不在常见语料中。
- **解决**：框架中配置 `asr_corrections` 纠错表，识别后直接替换。
- **后续**：可换支持热词的 ASR（讯飞 / Paraformer），或用 LLM 做上下文纠错。

#### 问题 6：固定违禁词抓不住话术变体
- **现象**：上次录音是"郑总临时加的"，今天直播是"王总来炸福利"，套路相同（虚构高管临时加赠，制造紧迫感），但换了说法，固定词就失效了。
- **解决思路**：词库只放确定性的违禁词；"虚构紧迫"这类语义问题交给 LLM，问题编码 `compliance:false`。这也是规则 + LLM 分层设计的直接例证。

#### 问题 7：模型接口报错对场控不可读，且每分钟重复弹窗
- **现象**：配置 DeepSeek 密钥后首次调用返回 `402 Payment Required`。原实现直接 `raise_for_status()`，界面只显示"Client error '402 Payment Required'…"，场控看不懂；而且每个分析周期都失败一次，每分钟弹一次窗。
- **原因**：402 的响应体是 `Insufficient Balance`，即账户余额不足（密钥本身有效，认证已通过）。
- **解决**：
  1. 新增 `LLMError`：解析响应体中的 `error.message`，按状态码翻译成中文提示（401 密钥无效 / 402 余额不足 / 429 频率或额度限制）；
  2. 去掉每次都不同的 `request_id`，界面据此判断"同一错误"，**只弹一次窗**，之后持续显示在 AI 面板里；下一次分析成功后自动清除；
  3. 面板明确提示"本地规则不受影响，继续运行"。
- **验证**：3 分钟样本 10 倍速回放，3 次分析全部失败，错误弹窗只出现 1 次，违禁词 / 语速告警照常产生。
- **复盘**：这是分层设计的好处——LLM 是"增强层"，挂掉时规则层照常工作；错误提示要面向使用者（场控），而不是面向开发者。

## D2（续）· AI 分析实测与调优

### 1. 打通过程
1. 首次调用返回 `402 Insufficient Balance`（账户余额不足），见问题 7；充值后接口正常。
2. 价格页已不再列出 `deepseek-chat`。发一个最小请求查看响应中的 `model` 字段，确认 `deepseek-chat` 现在由 **`deepseek-flash`** 提供服务，于是默认模型改为 `deepseek-flash`（旧名仍可用），成本也按 flash 档计算。
3. `_meta` 中增加 `cache_hit_tokens`（服务端缓存命中的输入 token），用于准确计算成本。

### 2. 单次分析质量（3 分钟样本）
- 耗时 4.8 秒，输入 1756 token、输出 783 token，评分 58。
- 抓到的问题都附了原文证据：功效宣称绝对化（"28 天…皱纹松弛下垂全部改善"）、未完整报价、过度施压逼单、虚构临时加赠（"郑总临时加的"被正确识别为虚构紧迫——这是固定词库做不到的语义判断）。
- 8 个阶段的覆盖情况和点评合理。

### 3. 问题 8：AI 把识别错误当成主播的问题（误报）
- **现象**：AI 报"规格表述混乱"，证据是"额外再赠你升级款 100 瓶水，100 秒乳"。实际主播说的是"100 毫升"，是语音识别错了。
- **尝试 1：提示词里强调数字 / 单位常被识别错** → 无效，第二次仍然报。
- **尝试 2：让模型对每个问题输出 `asr_suspect` 自检字段，代码过滤掉为 true 的** → 有改善但不稳定：
  - 第 1 次：正确过滤了"规格矛盾"，但把"未完整报价"（可能是真问题）也过滤了；
  - 第 2 次："规格矛盾"仍被保留。
  - 30 分钟测试中，自检字段一共过滤了 15～18 条问题。
- **结论**：提示词层面的手段能降低、但无法消除这类误报，而且以牺牲召回为代价（精确率与召回率的取舍）。保留自检字段，作为已知问题记录。
- **根本解决方向**：① 换支持热词的 ASR，从源头减少数字和品牌名错误；② 先用 LLM 结合上下文纠错转写，再分析；③ 建立人工标注的评估集，量化每次修改提示词的效果，而不是凭单次输出判断。

### 4. 问题 9：AI 和违禁词规则重复报同一个问题
- **现象**："全部改善"已被违禁词规则秒级告警，AI 又以"功效宣称绝对化"报一条，场控看到两条重复告警。
- **解决**：AI 的问题如果引用的原文和某条违禁词告警的原句相似，就合并进那条告警，标记为 **"AI 确认"**，并用 AI 给出的更具体的建议替换默认建议。
- **验证**：30 分钟测试中合并了 8～9 次。

### 5. 问题 10：告警去重的粒度——三轮实测
这是今天最有价值的发现：**去重规则直接决定场控看到的是信号还是噪音**，而两个方向都会出错。

| 版本 | 去重规则 | 30 分钟告警数 | 问题 |
|---|---|---|---|
| v1 | 按问题编码合并 | 30（约 1 条/分） | **漏掉新风险**："榜单第一无依据 ×20"里其实混进了各种不同的问题；"保价三年三倍退款""虚构央视报道"这类严重的新虚假宣传，因为编码相同被当作旧问题只加了次数，标题停在第一次，场控永远看不到 |
| v2 | 编码相同且原文证据相似才合并 | 83（约 2.8 条/分） | **太吵**：主播持续逼单，AI 每次引用不同的句子，"过度逼单"出现约 10 次、"未完整报价"出现 8 次 |
| **v3（采用）** | 合规类按证据合并，其余按编码合并 | **45（约 1.5 条/分）** | 状态型问题被压住（"过度逼单"只在第 1 分钟提醒一次，之后累加次数）；事件型新风险全部单独提醒：虚构榜单第一、保价三年三倍退款、赔 100 套、虚构央视报道、虚构专利依据。"保价三年"每隔约 5 分钟提醒一次（主播换说法反复讲），对反复违规定期再提醒是合理的 |

- **关键认知：问题分两种。**
  - **事件型**（合规类：虚假承诺、功效夸大、极限词）：每一个新的说法都是一次独立的风险事件，必须单独提醒；
  - **状态型**（内容、缺失、节奏类：持续逼单、一直没报价、缺互动）：是持续存在的状态，换一句话说仍是同一个问题，提醒一次、累加次数即可。
- **证据相似度**：用字符二元组的**包含度**（短的一段有 60% 以上的二元组出现在长的一段里），而不是 Jaccard，因为 AI 每次引用的片段长短不一。

### 6. 性能与成本（30 分钟样本，5 倍速回放，每 60 秒分析最近 5 分钟）

| 指标 | 实测 |
|---|---|
| 分析次数 / 失败 / 跳过 | 30 / 0 / 0 |
| 单次延迟 | 平均 4.7～4.9 秒，最长 5.6～6.9 秒（远小于 60 秒周期） |
| 单次 token | 输入约 2365，输出约 755～778 |
| 缓存命中率 | **93%**（系统提示词和框架每次相同，命中服务端缓存） |
| 实际服务模型 | deepseek-flash |

**每个直播间每小时成本**（60 次分析；输入约 14.2 万 token，其中 93% 命中缓存；输出约 4.6 万 token；价格来自 DeepSeek 官网价格页，deepseek-flash 档）：

| 时段 | 缓存命中输入 | 未命中输入 | 输出 | 合计 |
|---|---|---|---|---|
| 高峰（命中 0.04 / 未命中 2 / 输出 8 元每百万） | 0.005 元 | 0.020 元 | 0.37 元 | **约 0.39 元/小时** |
| 空闲（命中 0.02 / 未命中 1 / 输出 4 元每百万） | 0.003 元 | 0.010 元 | 0.18 元 | **约 0.20 元/小时** |

- **输出 token 占成本的 90% 以上**。后续优化方向：缩短 `stage_coverage` 的点评、减少问题数量上限，或者只在有新问题时才输出详细字段。
- 对比：如果没有缓存命中，高峰期约 0.66 元/小时。**保持系统提示词和框架在前、转写在后**（前缀不变）是缓存能生效的前提。

### 7. 其他观察
- **语速**：30 个周期在 306～393 字/分之间，2 次超过 380 的阈值触发告警（同一状态窗口内合并）。韩束这场整体语速偏快。
- **话术评分**：52～68 分，阶段长期停留在"促单逼单"，AI 反复指出"核心卖点缺失""连续逼单不讲产品"，与人工听感一致。
- **AI 发现的高价值风险**（规则层无法发现）：保价三年三倍退款、赔 100 套的承诺、虚构央视报道、虚构榜单第一、虚构高管临时加赠。

## D2（续二）· 锦上添花：在线人数曲线

### 1. 为什么做这个
前面的功能都在回答“主播哪里讲得不好”，但没法回答“讲得不好有什么损失”。把在线人数和语速、告警画在同一张图上，就能直接看出“冷场或者违规话术之后人有没有走”，把“查问题”往“证明问题有代价”推进一步。

### 2. 实现
- **数据来源**：抖音进房接口 `webcast/room/web/enter` 本来就在调，返回里的 `room_view_stats.display_value` 是精确的在线人数（`user_count_str` 是“600+”这种展示文案，不能用）。不需要新接口，也不需要弹幕长连接。
- **接口设计**：`StreamSource` 加了 `viewers(target, t) -> int | None`，默认返回 None。`t` 是音频时间：直播时忽略，回放时用它对齐录制时的人数。其他平台以后照这个接口实现。
- **采样时机**：放在每分钟的分析里，和语速指标一起取、一起存（`metrics.jsonl` 里的 `viewers` 字段）。这样人数和语速天然在同一个时间点上，不用单独起线程、单独对齐。请求失败只记日志，不影响分析。
- **回放也能看人数**：`scripts/record.py` 录音时每 30 秒取一次人数，写进 `<录音名>.viewers.jsonl`（`{"t": 音频秒数, "viewers": 人数}`）。`FileSource.viewers()` 读这个文件，用二分查找取 t 之前最近的一次。之前录的 30 分钟样本没有这个文件，图上会显示“无在线人数”。
- **图表**：左轴语速（蓝），右轴在线人数（紫，独立刻度，上下留 10% 余量，波动才看得出来），底部时间轴上标告警，颜色按严重程度。横轴从 00:00 开始，因为第一个周期前就可能有违禁词告警。
- **复盘报告**：有人数数据时多一张卡片，显示均值、峰值、最低值。

### 3. 遇到的问题
- **右侧刻度的颜色不生效**：SVG 的 `fill` 属性被全局 CSS `svg text{fill:...}` 覆盖了（CSS 规则优先级高于 SVG 的呈现属性），改成写内联 `style` 才生效。
- **告警标记叠在一起**：同一个周期产生的告警时间完全相同，8 条告警只看得到 3 根线。改成按横坐标合并：一根线，颜色取最严重的，旁边标数量，悬停显示全部标题。
- **结尾多出一个重复的点**：录音长度刚好是 60 秒的整数倍时，最后一个周期分析完，录音结束又触发一次“收尾分析”，同一时间点出现两个点，AI 也多调用一次。改成距上次分析不足 5 秒时跳过收尾分析。这个问题之前就有，这次画人数时才看出来。

### 4. 验证
- 真实直播间（韩束，10 月 27 日下午开播中）：4 个周期取到 599 → 619 → 624 → 660，图表正常。
- 同时录了 6 分钟新样本 `samples/295178185857_20261027_161922.wav`（录音和人数文件都不进 git），按 5 倍速回放：6 个周期人数 611 → 604 → 611 → 624 → 648 → 691，和录制时一致；报告里显示均值 640、峰值 691、最低 604。

### 5. 局限
- 人数每分钟一个点，看不到秒级的进出；人数变化也受投流、平台推荐影响，图上只能看出“同时发生”，不能直接说是话术导致的。
- 后续可以在人数短时间下跌超过某个比例时自动告警，并把“下跌前 1 分钟主播在讲什么”一起给出来。

## D2（续三）· 锦上添花：告警回听

### 1. 为什么做这个
前面记录过一个没解决的问题：AI 会把识别错字当成主播说错了（比如“100 毫升”识别成“100 瓶”，AI 报“规格混乱”）。提示词约束和 `asr_suspect` 自查只能减少，不能根除。与其继续让 AI 自己判断，不如让人 3 秒钟核实：每条告警都能点开听原声。

### 2. 实现
- **音频落盘**：会话把收到的 16kHz 单声道 PCM 原样追加写进 `sessions/<场次>/audio.pcm`，每 0.5 秒刷一次盘。不写 WAV 是因为 WAV 头里有总长度，边写边读麻烦；裸 PCM 的定位就是 `音频秒数 × 32000 字节`。断流重连时音频时间不前进，文件也不写入，所以时间和文件位置始终对得上。
- **切片接口**：`GET /api/rooms/{id}/audio?start=&end=`，按需从 PCM 里切一段，包成 WAV 返回。偏移按 2 字节（一个采样）对齐，否则会切出噪音。单段最长 30 秒。
- **每条告警算好回听区间**（`clip` 字段，和告警一起存）：
  - 违禁词：定位到这个词在句子里的位置，前后各 2 秒；
  - 冷场：`metrics` 新增 `max_gap_at`（最长冷场从哪一秒开始），听冷场前 3 秒到结束后 3 秒；
  - 语速、口头禅等：属于整段的状态，听周期最后 20 秒；
  - AI 告警：在窗口转写里找 AI 引用的原文（见下面问题 1），找不到就不显示回听按钮。
- **界面**：告警卡片右上角加“▶ 回听”，播放时变成“■ 停止”。告警栏和复盘报告共用一个播放器，点另一条会自动切换。

### 3. 遇到的问题
1. **按整句回听太长、定位不准**。最初按“包含引用的那一句”来切，但 VAD 切出的一句常有 10～40 秒（样本里最长 38 秒），一句 7 个字的引用“但只有三单了啊”会给出 0～30 秒的片段。还会误扩展到相邻句子：短引用的字符二元组很少，邻句随便就能命中 15%。
   - **改成按字定位**：把窗口里的转写拼起来，每个字按它在句子里的位置线性换算成时间；再找引用的二元组命中最密集、且跨度不超过引用长度的一段（双指针滑动窗口），前后各留 2 秒。跨句和截半句的引用都能处理。
   - 效果：AI 告警的回听片段从 15～30 秒缩短到 **5～10 秒**。
2. **怎么确认切得准**：把切出来的片段再交给 SenseVoice 识别一遍，看是否包含告警原文。6 分钟样本的 6 条 AI 告警、30 分钟样本的 2 条违禁词和 2 条 AI 告警，**10 段全部包含原文**。线性换算本身有几秒误差，但 2 秒余量够用。
3. **改完代码忘了重启服务**：第一次验证时还是旧结果，发现服务没有热重载。这里记一下：改 Python 代码后要重启预览服务。

### 4. 代价与局限
- 磁盘：每路直播每小时约 115MB（32KB/秒）。`sessions/` 不进 git，长期使用需要定期清理，或者以后改成压缩格式、只保留告警前后的片段。
- 回听只在本场会话内有效（接口按内存里的会话查找）；服务重启后，历史场次的音频还在磁盘上，但界面里打不开。
